## Keys identify rows and connect tables

A primary key uniquely identifies each row and cannot be NULL. A table has one primary-key constraint, which can contain one column or several columns.

~~~sql
CREATE TABLE store.coupon_codes (
    id bigint GENERATED ALWAYS AS IDENTITY,
    code text NOT NULL,
    discount_percent numeric(5, 2) NOT NULL,
    active boolean NOT NULL DEFAULT true,
    CONSTRAINT coupon_codes_pkey PRIMARY KEY (id),
    CONSTRAINT coupon_codes_code_key UNIQUE (code),
    CONSTRAINT coupon_codes_discount_check
        CHECK (discount_percent > 0 AND discount_percent <= 100)
);
~~~

Named constraints make error messages and later schema changes easier to understand. A foreign key makes a value refer to an existing row:

~~~sql
ALTER TABLE store.orders
ADD CONSTRAINT orders_customer_fkey
FOREIGN KEY (customer_id)
REFERENCES store.customers (id)
ON DELETE RESTRICT;
~~~

The chapter 2 schema already has an unnamed foreign key for customer_id, so run this statement only on a fresh schema where that constraint has not already been added. A real migration should inspect the existing constraint before adding another.

## Choose delete behavior deliberately

- RESTRICT prevents deleting a referenced parent row while a child exists.
- NO ACTION is the default and checks the constraint at the end of the statement, or at transaction end when the constraint is deferred.
- CASCADE deletes matching child rows when a parent is deleted.
- SET NULL or SET DEFAULT changes the child key according to its name, when the column definition allows that value.

CASCADE is appropriate only when the child has no independent history. Deleting a customer should not casually erase completed orders or financial records.

## Use constraints for rules about stored rows

NOT NULL requires a value. UNIQUE prevents duplicate values. CHECK requires a row expression to be true or NULL, so pair CHECK with NOT NULL when a missing value is invalid.

~~~sql
CREATE TABLE store.product_reviews (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    product_id bigint NOT NULL REFERENCES store.products (id),
    rating integer NOT NULL CHECK (rating BETWEEN 1 AND 5),
    body text,
    created_at timestamptz NOT NULL DEFAULT current_timestamp
);
~~~

By default, a unique constraint allows more than one NULL because NULL values are distinct for uniqueness. Use NOT NULL when the column must be present. PostgreSQL also supports NULLS NOT DISTINCT for a unique constraint when NULL should count as one shared value.

CHECK constraints are row-local rules. Do not use a CHECK subquery to enforce a rule across other rows. Use a unique constraint, foreign key, exclusion constraint, or a transaction-safe design for cross-row rules.

## Identity values and composite keys

GENERATED ALWAYS AS IDENTITY prevents ordinary inserts from supplying a value. GENERATED BY DEFAULT AS IDENTITY lets an insert provide one when needed. Identity values are backed by sequences, so gaps can occur after rolled-back or failed inserts. Do not use an identity sequence as a count of successful rows.

The order_items table uses a composite primary key: order_id plus product_id identifies one line for each product in an order. The key also creates an index on those columns in that order. It does not automatically create an index beginning with product_id.

PostgreSQL automatically indexes primary keys and unique constraints. It does not automatically index the referencing side of a foreign key. Add an index when child rows are frequently searched by that foreign key or when parent deletes and updates need to find them efficiently:

~~~sql
CREATE INDEX orders_customer_id_idx
ON store.orders (customer_id);

CREATE INDEX order_items_product_id_idx
ON store.order_items (product_id);
~~~

## Migrate constraints safely

Before adding a constraint to a populated table, check existing data for violations. For a large table, NOT VALID can add a foreign-key or check constraint without scanning all old rows immediately. VALIDATE CONSTRAINT checks existing rows later; new and changed rows are still checked after the constraint is added.

~~~sql
ALTER TABLE store.orders
ADD CONSTRAINT orders_status_check
CHECK (status IN ('pending', 'paid', 'cancelled')) NOT VALID;

ALTER TABLE store.orders
VALIDATE CONSTRAINT orders_status_check;
~~~

This status rule is useful only if these are the complete status values the application permits.
